Keep Every Pull Request Small

Every PR that needs a review must change at most 300 lines of production code, do one thing, and be mergeable on its own. This page says how to count, how to split, and how to name the PRs.

Context

01Why small pull requests

A large PR is slower to review, easier to get wrong, and harder to undo. Our CI also assumes a small PR that targets master.

What a large PR costs us

A recent withdrawal-risk PR changed 47 files and about 6,500 lines of production code (11,500 lines including tests and docs). It needed three review rounds and produced ten findings, among them a migration that would block writes on the hot ledger table and an alert that could never fire. Both are easy to miss in a diff that size and easy to catch in a 300-line PR.

  • Reviewers lose focus after a few hundred lines, so real problems hide among the routine ones.
  • A bug found late means rewriting a lot of dependent code.
  • One failing part blocks everything else in the PR from merging.
  • Rolling back a large PR also rolls back the good parts.
Repository facts

Only squash and rebase merges are enabled. Pull-request CI (tests, migration order, proto lint) runs only when the base branch is master, uat or release/**.

The rules

02The rules

Eight rules. The first one is the one reviewers will enforce.

Rules at a glance

#RuleDetail
1At most 300 added lines of production code per PRAim for 200 to 300. Tests, generated code, seed data and docs do not count (chapter 03). Over 300 needs an approved exception.
2One concern per PRIf the title needs "and", it is probably two PRs.
3Self-containedBuilds, all tests pass, and nothing changes in production behaviour unless the PR says so. A PR must not leave master broken or depend on an unmerged PR to pass.
4Base is always masterDo not stack a PR on another PR's branch and do not merge into a feature branch: CI does not run for those bases.
5A dependent PR is opened after its predecessor has mergedYou may write it locally earlier (chapter 07), but do not open it until the base is merged.
6Tests travel with the codeNo test-only PR, except to fill a coverage gap on code that is already merged.
7Title and description follow the templatesChapters 05 and 06. The first line of the description states the dependency and the size.
8New behaviour ships darkA PR that adds a capability must not change what users see until the final PR of the series turns it on.

Status of enforcement

Reviewers apply these rules by hand today. A CI size check and a size-exception label are PROPOSED and not live yet. Until they exist, please run the command in chapter 03 before you open a PR and paste the number into the description.

Measuring

03How to count the lines

Count added production lines only. Anyone can reproduce the number with one command.

The command

Run from your branch, after fetching master:

git fetch origin master
git diff --numstat origin/master...HEAD -- . \
  ':(exclude)*_test.go' ':(exclude)*.pb.go' ':(exclude)*.pb.gw.go' \
  ':(exclude)*/seeds/*' ':(exclude)doc' ':(exclude)docs' ':(exclude)*.md' \
  | awk '{a+=$1} END{print a" added production lines"}'

Use the same pattern for the description line, for example Production code: 241 added lines.

Checked

The command was run against a real PR in this repository and returns the number of added lines outside the excluded paths.

What counts

CountsDoes not count
Go source, SQL migrations, .proto definitions, YAML and JSON config, scripts, CI workflows, Helm valuesFiles ending in _test.go; generated *.pb.go and *.pb.gw.go; seed data under seeds/; doc/, docs/ and any .md file

Only added lines are counted. Deleting code is cheap to review, so a PR that mostly deletes can be larger, but ask for an exception first.

Exceptions

An exception needs a label size-exception and one sentence in the description saying why the change cannot be split. Reviewers may reject it. Accepted reasons:

  • A migration and the code that needs it must ship together to stay consistent.
  • A mechanical change with no logic, such as a rename across many files.
  • A pure deletion of dead code.

Not accepted: "it is all related", "splitting takes too long", "the tests are big".

Splitting

04How to split a task

Decide the split before writing code. Cut along seams that keep every PR safe on its own.

Five cuts that work

  1. Behaviour-neutral refactor first.Move or rename code in one PR with no change in behaviour, then change behaviour in the next.
  2. Add new code that nothing calls.A new function or file with its tests. Safe to merge: it is dark.
  3. Wire it in.A small PR that connects the new code to its callers.
  4. One service per PR.Do not mix quote, pm_perp and analytics in one change unless it cannot be avoided.
  5. Schema separate from use.A migration that adds a nullable column ships first; code that reads it follows.

Naming

05How to name a pull request

The squash-merge commit takes the PR title, so the title is what stays in history. Keep it short, specific and in the existing style.

Format

<type>(<scope>): [<ticket>] [<n>/<N>] <imperative summary>
  • type: feat, fix, refactor, perf, test, docs, ci or chore. This is already how the repository is written.
  • scope: the service or area, for example pm_perp, quote, analytics, trading-api, fee-engine. Several scopes are separated by a comma.
  • ticket: optional, for example [YEN-3757].
  • [n/N]: required when the PR belongs to a series, where N is the number of PRs in that group. This is new.
  • summary: English, imperative mood ("add", "move", "apply"), no trailing period, and 72 characters or fewer for the whole title.
Series

Number only within one group, for example group A of the XRP work is [1/3] to [3/3]. The group name goes in the scope or the summary so it can be found.

Good and bad

TitleVerdictWhy
feat(pm_perp): [1/3] group unrealized PnL by quote assetGOODType, scope, series marker, specific imperative summary.
feat(pm_perp,analytics): [YEN-3757] [2/4] add asset field to funding eventsGOODTicket and series marker together; two scopes because the change spans them.
feat: XRP perps (all changes)BADNo scope, no series, announces a giant PR.

Template

06The PR description

The first line tells the reviewer how big the PR is and what it depends on, so they can decide in ten seconds whether to start.

Template

Depends on: #1234   (or: none, can merge in any order)
Production code: 241 added lines   (command in chapter 03)
Series: group A margin grouping, 1 of 3

## What
One paragraph: what this PR changes and nothing else.

## Why
The reason, with a link to the design or ticket.

## Safety
What changes in production when this merges (ideally: nothing),
and how it is verified.

## Tests
The tests added or changed, and the command to run them.

## Not in this PR
The follow-up PRs, so reviewers do not ask for them here.
Language

Titles, descriptions, code comments and docs are English only.

Working in a series

07Working through a series

A series is several small PRs that together deliver one task. Each one targets master. Keep a status table so everyone can see where it stands.

The status table

The owner keeps two tables in the tracking issue: the PRs that are open, and the ones still planned. Update it whenever a PR opens or merges. Example format with illustrative numbers:

#PRFull titleStatus
[1/3]#1801feat(pm_perp): [1/3] group unrealized PnL by quote assetMerged
[2/3]#1805feat(pm_perp): [2/3] apply per-asset margin to the cross scannerIn review
[3/3](not opened)Planned: add the isolated_only flag and the order asset checkPlanned

For planned PRs write the scope only. The official title is set when the PR is opened.

Writing the next PR before the previous one merges

You do not have to wait idle. Branch from the predecessor locally, write and test the next PR, and keep it unpublished. After the predecessor is squash-merged, move your branch onto master and open it:

git fetch origin
git rebase --onto origin/master <last-commit-of-predecessor> my-next-branch
git push --force-with-lease -u origin my-next-branch
gh pr create --base master
Why not open it early

A PR whose base is another PR branch gets no CI here, and every squash-merge of the base forces a rebase. Opening it after the merge avoids both.

If the predecessor changes in review, rebase your local branch onto it again before you open yours. Keep at most one dependent PR written ahead.

For reviewers

08For reviewers

Reviewers are expected to push back on size before reading the code.

What reviewers do

  • If the description has no size line, ask for it.
  • If the number is above 300 and there is no approved exception, ask for a split. You do not need to review the code first.
  • If the PR does two things, ask for two PRs.
  • If a PR depends on something unmerged, ask the author to wait and open it after the merge.
  • Check the safety section: a PR in a series should change nothing in production unless it is the last one.
Before you open

09Checklist before opening a PR

Tick every line. If one fails, fix it before opening.

Checklist

  • The size command shows 300 added lines or fewer, and the number is in the description.
  • The PR does one thing and the title does not need "and".
  • Base is master, and every dependency is already merged.
  • The title follows type(scope): [n/N] summary, in English.
  • The description starts with the dependency and size lines and has a Safety section.
  • Tests for this code are in the PR, and the tests pass locally.
  • Without the later PRs in the series, nothing changes for users.
  • Any migration version is above the current master maximum.
