每个 PR 都要小

每个需要评审的 PR 必须最多改 300 行生产代码，只做一件事，并且能独立合并。本文说明怎么数行数、怎么拆、PR 标题怎么命名。

背景

01为什么要小 PR

大 PR 评审慢、容易出错、难以回退。我们的 CI 也默认是小 PR、目标是 master。

大 PR 的代价

最近一个提现风控 PR 改了 47 个文件，约 6,500 行生产代码（含测试和文档共 11,500 行），评审了三轮、提出十条问题，其中有一个会阻塞热点流水表写入的迁移，还有一个永远不会触发的告警。这两个问题在这么大的 diff 里很容易漏掉，在 300 行的 PR 里很容易发现。

  • 评审人看过几百行之后注意力下降，真正的问题会藏在常规改动里。
  • 问题发现得晚，依赖它的大量代码都要重写。
  • PR 里有一部分有问题，其余部分也合不进去。
  • 回退大 PR 时，好的部分也一起被回退。
仓库事实

只开了 squash 和 rebase 两种合并。PR 的 CI（测试、迁移顺序、proto 检查）只在 base 是 master、uat 或 release/** 时触发。

规则

02规则

共八条。第一条是评审人会执行的。

规则一览

#规则说明
1每个 PR 最多新增 300 行生产代码目标 200 到 300 行。测试、生成代码、种子数据和文档不算（第 03 章）。超过 300 行需要批准的例外。
2每个 PR 只做一件事标题里需要写"和"，通常说明是两个 PR。
3自成一体能编译，测试全绿，除非 PR 里说明，否则对线上行为没有任何改变。不能让 master 处于损坏状态，也不能靠未合入的 PR 才通过。
4base 永远是 master不要把 PR 叠在另一个 PR 的分支上，也不要合进功能分支：这些 base 不会触发 CI。
5有依赖的 PR，等前一个合入后再开可以提前在本地写好（第 07 章），但 base 合入之前不要开 PR。
6测试跟着代码走不单独做纯测试 PR，除非是给已合入的代码补覆盖。
7标题和描述按模板写见第 05、06 章。描述第一行写依赖和行数。
8新行为默认不生效增加新能力的 PR，在系列里最后一个 PR 打开之前，不能改变用户看到的任何东西。

执行状态

目前评审人手工执行这些规则。CI 的行数检查和 size-exception 标签是提议，还没有上线。在那之前，开 PR 前请先跑第 03 章的命令，把数字写进描述。

度量

03怎么数行数

只数新增的生产代码行。任何人用一条命令都能复现这个数字。

命令

在你的分支上执行，先拉取最新的 master：

git fetch origin master
git diff --numstat origin/master...HEAD -- . \
  ':(exclude)*_test.go' ':(exclude)*.pb.go' ':(exclude)*.pb.gw.go' \
  ':(exclude)*/seeds/*' ':(exclude)doc' ':(exclude)docs' ':(exclude)*.md' \
  | awk '{a+=$1} END{print a" added production lines"}'

描述里用同样的写法，例如 Production code: 241 added lines。

已验证

这条命令已经对本仓库里的一个真实 PR 跑过，返回的是排除路径之外新增的行数。

哪些算

计入不计入
Go 源码、SQL 迁移、.proto 定义、YAML 和 JSON 配置、脚本、CI 工作流、Helm values以 _test.go 结尾的文件；生成的 *.pb.go 和 *.pb.gw.go；seeds/ 下的种子数据；doc/、docs/ 以及任何 .md 文件

只数新增的行。删代码评审成本低，所以主要是删除的 PR 可以大一些，但要先申请例外。

例外

例外需要打 size-exception 标签，并在描述里用一句话说明为什么拆不开。评审人可以拒绝。可接受的理由：

  • 迁移和依赖它的代码必须一起发布才能保持一致。
  • 没有逻辑的机械改动，比如跨很多文件的重命名。
  • 纯删除无用代码。

不接受的理由："都是相关的"、"拆开太麻烦"、"测试太多"。

拆分

04怎么拆任务

先定拆分方案，再写代码。沿着能让每个 PR 单独安全的接缝去切。

五种有效的切法

  1. 先做不改行为的重构。用一个 PR 只挪动或重命名代码、行为不变，下一个 PR 再改行为。
  2. 新增没人调用的代码。新函数或新文件加上它的测试。可以安全合入：它还没生效。
  3. 接入。一个很小的 PR，把新代码接到调用方。
  4. 每个 PR 只改一个服务。除非无法避免，不要在一个改动里混合 quote、pm_perp 和 analytics。
  5. 表结构和使用分开。先发加可空列的迁移，再发读取它的代码。

示例：XRP 计价永续

XRP 方案拆成 5 组共 13 个 PR（B 组划转已由其他开发负责，不在本系列）。行数是按调用点估计的，不是实测，读完代码后再定稿。

命名

05PR 标题怎么命名

squash 合并的提交使用 PR 标题，所以标题就是留在历史里的内容。要简短、具体，并且沿用现有风格。

格式

<type>(<scope>): [<ticket>] [<n>/<N>] <imperative summary>
  • type：feat、fix、refactor、perf、test、docs、ci 或 chore。仓库现在就是这样写的。
  • scope：服务或模块，例如 pm_perp、quote、analytics、trading-api、fee-engine。多个 scope 用逗号分隔。
  • ticket：可选，例如 [YEN-3757]。
  • [n/N]：PR 属于一个系列时必填，N 是这一组的 PR 总数。这是新增的约定。
  • summary：英文，祈使句（"add"、"move"、"apply"），末尾不加句号，整个标题不超过 72 个字符。
系列

只在一组内编号，例如 XRP 的 A 组是 [1/3] 到 [3/3]。组名写在 scope 或 summary 里，方便检索。

好与不好

标题评价原因
feat(pm_perp): [1/3] group unrealized PnL by quote asset好有 type、scope、系列序号，summary 具体且是祈使句。
feat(pm_perp,analytics): [YEN-3757] [2/4] add asset field to funding events好ticket 和序号同时有；改动跨两个模块所以写了两个 scope。
feat: XRP perps (all changes)差没有 scope 和序号，一看就是巨型 PR。
fix(pm): wip差看不出改了什么。
feat(quote): derived market and funding rate and freshness check差一个标题里有三件事，应该拆开。
Update margin_manager.go差写的是文件名而不是改动，也不符合 type(scope) 风格。
模板

06PR 描述

第一行告诉评审人这个 PR 有多大、依赖什么，让他十秒钟内决定要不要开始看。

模板

Depends on: #1234   (or: none, can merge in any order)
Production code: 241 added lines   (command in chapter 03)
Series: group A margin grouping, 1 of 3

## What
One paragraph: what this PR changes and nothing else.

## Why
The reason, with a link to the design or ticket.

## Safety
What changes in production when this merges (ideally: nothing),
and how it is verified.

## Tests
The tests added or changed, and the command to run them.

## Not in this PR
The follow-up PRs, so reviewers do not ask for them here.
语言

标题、描述、代码注释和文档一律使用英文，所以模板也是英文。

按系列推进

07按系列推进

系列是若干个小 PR 合起来完成一个任务。每个都以 master 为目标。维护一张状态表，让大家都能看到进度。

状态表

负责人在跟踪 issue 里维护两张表：已开出的 PR，和还在计划中的 PR。每次开 PR 或合并时更新。格式示例（编号为示意）：

#PR完整标题状态
[1/3]#1801feat(pm_perp): [1/3] group unrealized PnL by quote asset已合并
[2/3]#1805feat(pm_perp): [2/3] apply per-asset margin to the cross scanner评审中
[3/3]（未开）计划：新增 isolated_only 开关和下单币种校验计划中

计划中的 PR 只写范围。正式标题在开 PR 时再定。

前一个没合入时，先写下一个

不用干等。在本地从前一个 PR 的分支拉出分支，把下一个 PR 写好、测好，但先不发布。前一个被 squash 合入之后，把你的分支挪到 master 上，再开 PR：

git fetch origin
git rebase --onto origin/master <last-commit-of-predecessor> my-next-branch
git push --force-with-lease -u origin my-next-branch
gh pr create --base master
为什么不提前开

base 是另一个 PR 分支的 PR 在这里没有 CI，而且前一个每次 squash 合并都会逼你 rebase。等合入之后再开，两个问题都避免了。

如果前一个 PR 在评审中有改动，开自己的 PR 之前要重新 rebase 本地分支。最多提前写一个有依赖的 PR。

给评审人

08给评审人

评审人应当先在大小上把关，再看代码。

评审人怎么做

  • 描述里没有行数，要求补上。
  • 数字超过 300 行又没有批准的例外，要求拆分。不需要先看代码。
  • PR 做了两件事，要求拆成两个 PR。
  • PR 依赖没合入的内容，要求作者等合入后再开。
  • 检查"Safety"部分：系列里的 PR 除了最后一个，不应该改变线上任何东西。
开 PR 之前

09开 PR 之前的清单

每一条都要满足。有一条不满足，先改好再开。

清单

  • 行数命令显示新增不超过 300 行，数字已写进描述。
  • PR 只做一件事，标题里不需要写"和"。
  • base 是 master，所有依赖都已合入。
  • 标题符合 type(scope): [n/N] summary，且是英文。
  • 描述第一行写了依赖和行数，并有 Safety 部分。
  • 这段代码的测试在 PR 里，且本地通过。
  • 系列里后面的 PR 还没合入时，用户看到的东西没有变化。
  • 迁移版本号大于当前 master 里的最大版本。
仓库的事实（合并方式、哪些工作流对哪些 base 分支触发）已于 2026-11-19 在 layer-3/neodax 里核实。标记为"提议"的项目 CI 还没有强制执行。
