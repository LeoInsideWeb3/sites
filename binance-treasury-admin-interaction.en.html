Binance treasury transfers: operator interaction

How an operator funds the Binance account from custody, and sweeps funds from the transit address back to custody, in the admin console. The backend in neodax PR #1868 supports the whole flow; the console pages do not exist yet. This document describes the proposed pages against the real API so the interaction can be confirmed before they are built. Section 12 lists the 15 points that need an answer.

02What an operator can do

Two kinds of transfer, each proposed by one person and approved by another. The operator chooses the asset, the amount and a reason. Everything else is fixed.

  • Funding: custody contract, then the transit address, then the Binance deposit address. Two on-chain legs.
  • Sweep: transit address back to the custody contract. One on-chain leg.

What the operator cannot set

The request carries no address, network or key. The destination address, the chain, the per-transfer minimum and maximum and the daily limits all come from a fixed profile held by Cage. The console only displays them.

The six actions

  • Propose a funding
  • Propose a sweep
  • Approve a proposal made by someone else
  • Reject a proposal made by someone else
  • Cancel your own proposal
  • Abandon a stalled operation whose current leg was never sent
CODERoutes: admin/router/platform_finance.go. Handlers: admin/api/platform_finance/binance_treasury.go. The comment on the API type states that requests never carry addresses, networks or keys.
NOT THIS FLOWneodax PR #1775 is about risk review of user withdrawals. It is unrelated to treasury transfers.

04States and actions

An operation has ten possible states in Admin. Only the first one accepts an operator decision. After approval everything is automatic until the operation completes, fails or stalls.

approval_pending ─ approve ─▶ approved ─ dispatch ─▶ executing ─▶ completed
  ├─ reject ─▶ rejected
  ├─ cancel ─▶ cancelled
  └─ 24 h   ─▶ expired

approved      ─▶ failed_retryable ─ auto retry ─▶ executing
approved      ─▶ failed_terminal   # Cage refused it
executing     ─▶ manual_review     # Cage reports a stall
manual_review ─ abandon ─▶ failed_terminal
manual_review ─ leg makes progress ─▶ executing
executing     ─▶ failed_terminal   # a leg failed for good

State values are lowercase strings in the API, for example approval_pending.

What the backend checks on submit

  1. Feature flagFunding and sweep have separate flags. If the flag is off the request fails.
  2. Required fieldsAsset and reason must not be empty. Amount must be positive.
  3. Cage profileThe profile must be configured and execution enabled. The asset must be in the profile.
  4. Amount boundsBetween the asset's minimum and maximum.
  5. Sweep only: sweepable balanceNot more than the sweepable balance of the transit address, when Cage knows that balance.
  6. Idempotency keyRequired. The same key with the same content returns the existing proposal. The same key with different content is a conflict.

The daily limit is not checked when proposing. It is checked at approval and enforced by Cage.

06Approve, reject, cancel

All three act only on an operation in approval_pending. They are buttons in the operation detail.

Approve

  • The approver is not the proposer.
  • The feature flag for this kind is still on.
  • The Cage profile is still configured and enabled, and its id and fingerprint match the ones stored with the proposal.
  • Amount approved today for this kind and asset, plus this amount, does not exceed the daily limit.

The approval record, the state change and the message that sends it to Cage are written in one database transaction. The reason is optional for approve.

Reject

Needs a reason. The proposer cannot reject their own proposal; they cancel it instead.

Cancel

Only the proposer. No reason field in the API.

Expiry

A proposal nobody decided on moves to expired 24 hours after it was created. The background worker does this, so the change appears within a few seconds of the deadline.

TRY ITSee this step in the interactive mockup.
DAILY LIMIT IS ADVISORY HERETwo approvers acting at the same moment can both pass this check. Cage enforces the real limit under a lock. The approval that loses is refused by Cage and ends as failed_terminal with DAILY_LIMIT_EXCEEDED. No extra funds move.

07Track execution

After approval nobody clicks anything. The detail view is where an operator watches progress.

  1. Dispatch, within about 2 secondsAn Admin background worker sends the approved operation to Cage, signed with a shared key. Only one Admin replica does this at a time.
  2. Cage accepts or refusesCage checks the signature, then the profile, amount bounds, daily limit and, for a sweep, the sweepable balance. For a funding it also checks that the custody withdrawal breaker is closed. A refusal ends the operation as failed_terminal.
  3. Funding leg 1: custody to transit addressCage starts a custody withdrawal to the transit address and waits for it to be final.
  4. Funding leg 2: transit address to BinanceThe transit address sends the tokens to the Binance deposit address. If the transaction stays unmined, Cage raises the fee, up to a configured cap.
  5. Sweep: one legThe transit address sends the tokens back to custody.
  6. CompletedWhen the last leg is final, the amount is added to the net-flow totals exactly once.

08Manual review

An operation enters manual_review when Cage reports it stalled. This is the only state after approval where an operator may act.

Why an operation stalls

  • A leg kept failing with the same kind of error for longer than the configured stall time (30 minutes in the sample config).
  • A transit-address transaction was mined but reverted more times than allowed (2 in the sample config).

Cage keeps working a stalled operation. If the leg then makes progress, the operation returns to executing on its own.

  • The Admin state is manual_review and the Cage state is STALLED.
  • The current leg was never signed or sent. If it was, Cage refuses with LEG_BROADCAST: the transaction must reach finality and cannot be abandoned.
  • A reason is given.

After an abandon the operation ends as failed_terminal. If no leg was final, the amount is released from the daily usage.

Funds left at the transit address

If a funding is abandoned or fails after leg 1 was final, the money is at the transit address. It stays there. Getting it back is a normal sweep: proposed by one person and approved by another.

09Profile and health

The top of the page tells an operator whether a transfer can work right now, before they propose one.

Per asset

  • Minimum and maximum per transfer.
  • Daily limit and amount used today, separately for funding and sweep.
  • Balance at the transit address, and how much of it can be swept.
  • Amount in transit: fundings whose first leg is final and whose second is not.
  • Net transferred to Binance: confirmed outbound minus confirmed returned. This is a record of what moved through this workflow. It is not the Binance account balance and it can be negative.

Warnings the page must show

  • BLOCKExecution is disabled in Cage, or the profile is not configured. Proposing is refused.
  • BLOCKEvidence ingestion is halted. States on this page may be out of date until an engineer resolves it. Show the halt reason and the blocking event.
  • WARNGas status of the transit address is LOW or BELOW_RESERVE. Transfers from it may not go out.
  • WARNBalances are stale or unknown. The sweepable amount shown may be wrong.
  • WARNEvidence lag is above zero for more than a short time.
GAS STATUSOne of OK, LOW, BELOW_RESERVE, UNKNOWN. Topping up gas on the transit address is outside this workflow.
INGESTION HALTAdmin stops reading Cage evidence when a row refers to an operation Admin never sent, or does not match what was approved. It never skips the row on its own. GET /ingestion returns halted, halt_reason (unknown_operation, evidence_drift, apply_error), halted_event_id and lag.
TO CONFIRM · Q12, Q15Which "used today" number to show, and who is told when ingestion halts.

10API reference

All paths are under /platform-finance/binance-treasury in admin-service. They need a logged-in admin and a Casbin rule. The migration in PR #1868 grants all eleven to role 1.

Responses use the usual envelope: code is 0 on success, and on failure message carries the text shown in section 11.

FIELD NAME CASINGThe operation's own fields come back in Pascal case (ID, State, OperationType, ProposerUsername, CreatedAt) because the Go struct has no JSON tags. The nested details, execution, approvals, evidence and cage use snake case. The existing dashboard type PlatformFinanceOperation already follows this.
NOT PUBLICadmin-service is reachable only inside the private network. None of these endpoints is exposed to the internet.

13Before it can be used

The backend logic is in place but operators cannot use it yet.

  • OPENPR #1868 is not merged. It has changes requested. One review finding is still open and was called a blocker by the reviewer: a column was added by editing a migration that may already have run in some environments.
  • OPENThe console pages in this document are not built.
  • CONFIGBoth feature flags in Admin are off by default, and Cage has its own profile and execution flags.
  • CONFIGOperations has to provide the shared signing key, the transit address and its key, and the asset list in the Cage profile. The sample config has an empty asset list.
  • OPSThe transit address needs gas. Topping it up is not part of this workflow.

What was verified for this document

Every statement about the backend comes from reading the code of PR #1868 at commit 914bb438. Nothing was run: no tests and no environment. The page layouts are proposals and do not exist in code.
